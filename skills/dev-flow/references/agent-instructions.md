# 子 agent 指令模板（dev-flow 核心资产）

编码 agent 与验收 agent 的完整指令模板、失败分类细则、迭代控制与落盘约定。
主 agent 编排时按此生成子 agent 的 task 文本。

## 编码 agent 指令模板（worker agent）

**输入（给编码 agent 的 task 里必须包含）**：
- 需求文档路径（必读，唯一规格源）
- 验收清单路径（自测参考）
- 工作目录/仓库
- 负责模块清单 + 开发顺序（按 A2 依赖）

**指令**：
1. 只编码：改代码/测试/配置；**禁止改需求文档和验收清单**。验收标准有疑问 → 回报主 agent，走 prd-md 变更流程，不静默修改
2. 涉及前端样式/UI 编码时：先读取并遵循前端设计技能（按任务类型从 ~/.agents/skills/ 选择 frontend-design / design-taste-frontend / high-end-visual-design / minimalist-ui / impeccable / redesign-existing-projects 等），并读取项目 DESIGN 规范（如 DESIGN.md）；禁止输出模板化/通用化样式
3. 涉及后端/API/服务端编码时：先读取并遵循后端技能——api-and-interface-design（设计 API/接口/模块边界时）、security-and-hardening（处理用户输入/认证/数据存储/外部集成时）；API 端点遵循需求文档 B4 冻结的 seams
4. 先读取 tdd 技能（~/.agents/skills/tdd/SKILL.md，及其 tests.md / mocking.md）再开始写测试：对 `[单测]`/`[数据脚本]` 类验收项**先写测试再实现**（红→绿）；测试期望值来自**验收清单的业务口径**（如"受淹面积 = 承保面积 × 村受淹比例"），不从实现倒推（防同义反复）；按需求文档 B4 冻结的 **seams** 写测试，不另选 seam；遵循 tdd 技能的反模式约束（禁止实现耦合/同义反复/水平切片）
5. 自测边界：`[单测]`/`[数据脚本]` 必须自己跑过；`[E2E-自动化]` 能跑就跑；`[E2E-人工]` 只做冒烟
6. checkpoint：完成一个独立模块且自测通过 → git commit（用 commit-work 技能，提交信息清晰）
7. 完成报告：改了哪些文件、每个模块自测结果、遗留问题

**禁止**：声称"验收通过"（验收权在验收 agent，你只有自测结果）。

## 验收 agent 指令模板（reviewer agent）

**输入（给验收 agent 的 task 里必须包含）**：
- 验收清单路径（**唯一验收依据**）
- 运行/启动命令（如何启动服务、如何跑测试）——主 agent 优先从项目 AGENTS.md 的验证命令章节提取后传入；验收 agent 可补充读取项目 AGENTS.md 的验证命令部分（限定：只读验证命令/运行章节，不读实现代码、不读需求文档）
- 工作目录

**指令**：
1. fresh context：**只看验收清单和运行命令，不读实现代码、不读需求文档描述**——验收的是行为，不是设计意图
2. **独立设计补充测试**：先从验收清单推导补充测试用例（重点：异常/边界路径、编码 agent 可能遗漏的场景），新增为独立测试文件（不修改已有测试）；跑补充测试 + 重跑已有测试
3. 逐条核对：每条验收项 → 通过 / 失败 / 未执行 + 证据（命令输出/截图/操作记录，含补充测试结果）
4. `[E2E-人工]` 类：不自行声称通过，标记"待人工确认"，附操作说明
5. 验证层级按清单标注执行；**未执行 = 不通过**
6. 禁止：改实现代码、改已有测试；补充测试只允许新增独立文件
7. 禁止自称人工验证

**输出**：按 templates/acceptance-report.md 模板生成结构化验收报告——逐条（编号 | 状态 | 证据 | 失败原因）+ 失败原因摘要 + **补充测试用例清单及结果** + 人工确认项清单。完成后报告主 agent。

## 失败分类细则（主 agent 判断）

| 失败类型 | 判定（报告里失败原因指向） | 处理 |
|---|---|---|
| 编码 bug | 实现不符合验收项 | 回编码 agent，附**失败项清单**（明确修哪些） |
| 需求缺陷 | 验收项无法执行/口径错误/验收项本身有问题 | 回 prd-md 变更流程，不静默改验收清单 |
| 环境/数据 | 数据未就绪、服务起不来、测试环境问题 | 主 agent 处理或升级用户，修好重验 |

**升级规则**：同一验收项连续失败 2 次 → 升级用户决策（回需求/换方案/继续），不等总上限。

**回编码方式**：默认 resume 原编码 subagent（保留上下文，任务 = 失败项清单 + 修复这些项）；当失败原因表明实现思路根本性错误（架构方向不对、无关改动过多）时，fresh 重启新编码 subagent，附失败清单 + 关键上下文摘要。判断权在主 agent，默认 resume。

## 人工验收项确认闭环（[E2E-人工]）

1. 验收报告中的"待人工确认"项 → 主 agent 呈现给用户（附操作说明）
2. 用户按操作说明验证 → 确认 通过 / 不通过
3. 主 agent 更新验收报告状态（待人工确认 → 用户确认通过 / 用户确认失败）
4. 全部通过（含人工项已确认）→ goal_complete；有人工项失败 → 按失败分类处理（实现问题回编码；验收项本身问题走需求缺陷回流）

## 需求缺陷回流执行路径

- 触发：验收失败分类为"需求缺陷"（验收项无法执行/口径错误/验收项本身有问题）
- 执行：主 agent 拿失败项清单与用户确认改法（对话中确认，不必重开完整 prd-md 对话）→ 用户拍板后同步修改需求文档 + 验收清单（编号绑定，改 B3/B4 必须同步改清单）→ 更新 A4 确认记录
- 改完 → 重新验收；若改动影响已实现模块，按影响范围决定是否重编码

## 迭代控制

- 编码→验收循环 ≤ 3 轮
- 每轮失败必须输出**失败原因摘要**（哪些验收项失败、为什么）
- 超限 → 停止循环，汇总给用户决策

## 落盘约定（默认路径，项目既有约定优先）

| 产物 | 默认路径 |
|---|---|
| 需求文档 | `<项目文档目录>/requirements/<名称>-V<N>需求.md` |
| 验收清单 | `<项目文档目录>/requirements/<名称>-V<N>验收清单.md` |
| 验收报告 | `<项目文档目录>/archive/验收记录-<名称>-V<N>.md` |

执行前先检查项目 AGENTS.md / docs README 的既有约定，有则遵循（如既有 `docs/requirements/` + `docs/archive/` 结构则直接沿用）。

## 长时间运行保障（编码/验收 subagent）

- async:true 是基础，但**单个 async child 默认 30 分钟超时**（DEFAULT_ASYNC_TIMEOUT_MS 硬编码，无官方 null 开关）——启动编码/验收 agent 时 timeoutMs = 86400000ms（24 小时）为上限，禁止依赖默认
- 等待子 agent 完成用 subagent_wait：其默认 timeoutMs 也是 30 分钟，等待长任务时传同样 86400000ms；交互式会话建议 `nonBlocking: true` 订阅（返回控制权，完成时自动唤醒）
- 禁止给编码/验收 agent 设紧的 turnBudget / toolBudget / usageBudget（pi-subagents 保守策略：mutation worker 被打断后应 checkpoint，不设紧预算）
- 即使超时也不是重来：resume 可从持久化会话续跑；编码 agent 每模块 commit（checkpoint），中断损失最多一个模块，配合状态文件（O2）跨会话恢复

## 与 goal 模式的对接

- goal 激活即进入 dev-flow 流程：goal 文本 = 需求文档路径 + "执行 dev-flow，验收清单全部通过才算完成，完成后汇报验收报告"
- goal 的完成条件 = 验收清单全部通过（人工项已由用户确认）
- 主 agent 角色 = 编排者 + 最终判断者，不亲自写代码
- 模块 commit 由编码 agent 执行（goal 模式的"模块完成→测试→commit"硬约束与 checkpoint 规则天然一致）

## 流程状态文件（O2）

- 路径：默认 `<项目文档目录>/.dev-flow-state.json`（项目既有约定优先），模板见 templates/dev-flow-state.json
- 维护时机：进入每个阶段更新 phase；每轮验收完成更新 iteration 和 acceptanceReports；全部通过后 status=done
- 跨会话恢复：主会话中断/重启后，先读状态文件确认当前阶段，再继续编排（不重新开始）
- 状态文件与验收报告都是事实来源：以文件为准，不以聊天记忆为准
